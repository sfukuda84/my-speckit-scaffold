# speckit-common-feature スキル（共通基盤 → 000-app-basic）

コアドメイン以外の共通機能（認証、メール送信など）の要件を、1 つの機能概要 `docs/feature/000-app-basic.md` にまとめる。`000` は予約番号であり、すべての機能より先に仕様化・実装する。

## 0. 大原則

- **コアドメインの機能を持ち込まない。** ここに入れるのは、どのサービスでもほぼ同じ形で必要になる共通機能だけである。サービス固有のロール、業務データ、初期設定は、それぞれの機能に残す。
- **技術選定はしない。** 使うサービスや方式は `docs/architecture.md` に従う。ここでは「何ができればよいか」を書き、方式の違いが要求に効く場合（例: ソーシャルログインの有無）だけ、要求として書く。
- **根拠のないものは入れない。** 根拠にしてよいのは、`premises.md` の「共通基盤の候補」、各機能の要求、`docs/architecture.md`、ユーザーの回答である。
- **書き出す前に合意を取る。**
- **記述の粒度は `speckit-concept-2-feature` と同じ**（広く浅く）。カラムの型、API のパス、数値パラメータは書かない。
- ドキュメントは日本語で書く。

## 1. 引数と入出力

```text
$ARGUMENTS
```

| 入力 | 用途 |
|---|---|
| `docs/feature/premises.md` の「共通基盤の候補」 | 000 に入れる候補と、必要とする機能 |
| `docs/feature/*.md`、`README.md`、`spec_order.md` | 各機能の要求と依存 |
| `docs/architecture.md` | 認証、メール、ストレージなどで採用した方式 |
| `.specify/memory/constitution.md` | 憲章の原則 |

| 出力 | 内容 |
|---|---|
| `docs/feature/000-app-basic.md` | 共通基盤の機能概要。様式は [`speckit-concept-2-feature` の templates/feature.md](../speckit-concept-2-feature/templates/feature.md) |
| `docs/feature/README.md` | 一覧の先頭に 000 の行を足す |
| `docs/feature/spec_order.md` | 先頭に `- **0. [<名称>](./000-app-basic.md)**: <一言>` を足す |
| 各機能ファイル（状態が「未着手」のもの） | `**依存**` に `000-app-basic` を足す |
| `docs/feature/premises.md` | 「共通基盤の候補」の各行に、000 に入れたかどうかを書き足す |

`000-app-basic.md` がすでにある場合は、**更新モード**として §4 に従う。

## 2. 手順

### ステップ 1: 候補の洗い出し

`premises.md` の「共通基盤の候補」と各機能の要求から、候補を洗い出す。次の一覧で漏れがないかも確かめる。

| 区分 | 候補 |
|---|---|
| 認証 | サインアップ、ログイン、ログアウト、パスワードの再設定、メールアドレスの確認、多要素認証、ソーシャルログイン、パスキー |
| アカウント | プロフィールの編集、メールアドレスの変更、退会とデータの削除 |
| 組織と権限 | 組織（テナント、Workspace）の作成、メンバーの招待、ロールと権限の仕組み（ロールの中身は各機能で決める） |
| 通知 | トランザクションメール（確認、再設定、招待など）、アプリ内通知、プッシュ通知 |
| ファイル | アップロード、ダウンロード、容量の制限 |
| 運営 | 運営者向けの管理画面（利用者の検索、停止）、監査ログ、お問い合わせ |
| 法務 | 利用規約とプライバシーポリシーへの同意、同意の履歴、Cookie の同意 |
| 課金 | プランと支払い（premises P9 で課金がある場合） |
| 共通 UI | エラー画面、メンテナンス表示、多言語、タイムゾーン |

### ステップ 2: 範囲のヒアリング

AskUserQuestion で、候補ごとに「MVP で入れる / 後で入れる / 入れない」を決める。1 ラウンド最大 4 問、推奨案を先頭に置く。

- 各機能の要求から必要と判断できるものは、根拠（機能名）を添えて推奨する。
- `docs/architecture.md` で採用したサービスが標準で提供するもの（例: 認証サービスのパスワード再設定）は、その旨を添える。
- 「後で入れる」ものは `docs/concept/backlog.md` の候補に足す（様式は `speckit-concept-2-feature` の templates/backlog.md）。

### ステップ 3: 大きさの確認

000 は `/speckit-specify` に 1 回で渡せる大きさにする（P1 のユーザーストーリーが 1〜3 本）。

- 大きすぎる場合は、MVP に必須のもの（通常は認証とトランザクションメール）だけを 000 に残し、残りは通常の番号の機能（既存の最大値の次から）に分ける。分けた機能は `000-app-basic` に依存させる。
- 分け方をユーザーに提示し、合意を取る。

### ステップ 4: 書き出し案の提示と合意

次をまとめて提示し、承認を得る。

1. 000 の主な要求（区分ごと）
2. スコープ外にするもの（後で入れるもの、入れないもの、各機能に残すもの）
3. 依存に `000-app-basic` を足す機能の一覧
4. 分けた機能がある場合は、その一覧

### ステップ 5: 書き出し

- `000-app-basic.md` を書く。ヘッダは `**状態**: 未着手 | **区分**: MVP | **想定順序**: 0 | **依存**: —` とする。H1 は「アプリ基盤」など、サービスに合った日本語名にする。
- 「前提・設計原則との関係」には、`docs/architecture.md` の該当節（認証方式、メール送信など）を書く。
- 「/speckit-specify に渡す記述案」を書く。
- `README.md` の一覧、`spec_order.md`、各機能の依存、`premises.md` を §1 の表どおりに更新する。状態が `spec化済み` 以降の機能は変更せず、影響があれば報告する。

### ステップ 6: 検証

```bash
python3 <skills>/speckit-concept-2-feature/scripts/validate.py docs/feature
```

`<skills>` は、このスキルが置かれた skills ディレクトリである。`python3` がない環境では `python` または `py -3` に読み替える。エラーが 0 件になるまで直す。000 に依存していない機能の警告は、意図どおりなら理由を報告に書く。

### ステップ 7: 報告

- 000 に入れた共通機能と、スコープ外にしたもの
- 更新したファイルと、依存を足した機能
- 検証の結果
- 次の手順の案内（`speckit-nfr-feature` で非機能要件を定義する。`speckit-bootstrap` の中で実行している場合は、その手順に戻る）

## 3. 記述の規則

- 共通機能の「どう作るか」（ライブラリ、テーブル、API）は書かない。
- ロールの中身（どのロールが何をできるか）は、各機能やアプリ固有の機能で決める。000 では「ロールと権限を割り当てられる仕組み」までを書く。
- 各機能が 000 の何を使うかは、各機能の「前提・設計原則との関係」に書き足してよい（状態が「未着手」のものに限る）。

## 4. 更新モード

`000-app-basic.md` がすでにある場合は、次のように進める。

- 状態が「未着手」なら、追加・変更の差分案を示し、承認されたものだけ反映する。
- 状態が `spec化済み` 以降なら、000 は書き換えない。追加が必要なものは、通常の番号の新しい機能として提案する。

## 5. 禁止事項

- コアドメインの業務機能を 000 に入れること
- 技術選定を 000 に書くこと（`docs/architecture.md` に従う）
- ユーザーの合意なしに書き出す、または上書きすること
- 状態が `spec化済み` 以降の機能ファイルを書き換えること
- 既存の機能の番号を振り直すこと
