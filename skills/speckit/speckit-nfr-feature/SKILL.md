# speckit-nfr-feature スキル（非機能要件 → docs/nfr.md ＋ 999-app-nfr）

非機能要件を、性質の違う 2 つに分けて書く。

| 出力 | 中身 | 使われ方 |
|---|---|---|
| `docs/nfr.md` | **横断要件**。全機能が守る目標と基準（稼働率、応答時間、パスワードの基準、ログに残してよい情報など） | 憲章と steering から参照され、各機能の `spec.md` と `plan.md` が従う |
| `docs/feature/999-app-nfr.md` | **運用基盤**。実装が必要な仕組み（監視とアラート、バックアップとリストア、CI/CD、ログの集約、脆弱性の検査など） | 通常の機能と同じく `speckit-all` などで仕様化・実装する |

`999` は予約番号である。ほかの機能は 999 に依存しない。

## 0. 大原則

- **構成と費用に見合う目標にする。** 目標値は `docs/architecture.md` で採用した構成と月額で達成できる水準にする。例えば VPS 1 台の構成で稼働率 99.99% は約束しない。構成を変えないと達成できない目標をユーザーが求めた場合は、その旨と `speckit-architecture` の見直しを提案する。
- **MVP 時と成長時に分ける。** 各目標に、MVP 時の値と、成長時（`docs/architecture.md` の「見直しの条件」に達した後）の値を書く。
- **測れる形で書く。** 「高速に」「安全に」ではなく、数値、条件、確認方法を書く。
- **書き出す前に合意を取る。**
- ドキュメントは日本語で書く。

## 1. 引数と入出力

```text
$ARGUMENTS
```

| 入力 | 用途 |
|---|---|
| `docs/architecture.md` | 構成、費用、監視やバックアップの方式、見直しの条件 |
| `.specify/memory/constitution.md` | 憲章の原則 |
| `docs/feature/000-app-basic.md` | 共通基盤の範囲（認証、監査ログなど） |
| `docs/feature/premises.md` | P6（セキュリティ・法規制）、P7（リソース要件）、P8（MVP の範囲） |
| `docs/feature/*.md` | 各機能の要求（性能やデータ量に効くもの） |

| 出力 | 様式 |
|---|---|
| `docs/nfr.md` | [templates/nfr.md](./templates/nfr.md) |
| `docs/feature/999-app-nfr.md` | [`speckit-concept-2-feature` の templates/feature.md](../speckit-concept-2-feature/templates/feature.md) |
| `docs/feature/README.md`、`spec_order.md` | 999 の行を足す |
| `.specify/memory/constitution.md` | `docs/nfr.md` を参照する条項がなければ、`speckit-constitution` の手順で足す |

どちらかがすでにある場合は、**更新モード**として §4 に従う。

## 2. 手順

### ステップ 1: 読み込み

入力を読み、次を整理する。

- 構成の制約（単一サーバーか、マネージドサービスの SLA はどうか、バックアップの仕組みはあるか）
- 扱うデータの性質（個人情報の区分、保存期間、消えたときの影響）
- 利用のされ方（業務時間中だけか、常時か、ピークの時間帯）

### ステップ 2: ヒアリング

次の区分ごとに、決まっていない目標を AskUserQuestion で聞く。1 ラウンド最大 4 問、推奨案を先頭に置く。推奨案は、構成と費用で達成できる値にする。

| 区分 | ID の接頭辞 | 決めること（例） |
|---|---|---|
| 可用性 | `NFR-AV` | 稼働率の目標、計画停止の扱い、障害時の目標復旧時間（RTO） |
| データ | `NFR-DA` | 目標復旧時点（RPO）、バックアップの頻度と保持期間、リストアの確認、データの保持と削除 |
| 性能・拡張性 | `NFR-PE` | 主要な画面・API の応答時間、同時利用者数、データ量の増加への対応 |
| セキュリティ | `NFR-SE` | 認証の強度、通信と保存の暗号化、脆弱性対策の基準（OWASP Top 10 など）、秘密情報の管理、権限の最小化、監査ログ |
| 運用・保守性 | `NFR-OP` | 監視する項目とアラートの宛先、ログの保持期間、デプロイの方法と頻度、依存ライブラリの更新、障害対応の手順 |
| 法令・コンプライアンス | `NFR-CO` | 個人情報保護法など適用される法令、データの保管場所、利用規約とプライバシーポリシー |
| 互換性・アクセシビリティ | `NFR-UX` | 対応するブラウザと端末、アクセシビリティの基準 |
| コスト | `NFR-CT` | 月額の上限、上限を超えそうなときの対応 |

- 000 と重なる項目（認証、監査ログなど）は、000 を機能の要求とし、`docs/nfr.md` にはその基準（パスワードの長さの下限、ログの保持期間など）だけを書く。
- CI/CD の最小構成（テストの自動実行）を早く入れたい場合は、000 が「未着手」ならその要求に足すか、999 で扱うかを質問する。

### ステップ 3: 横断要件と運用基盤への仕分け

決めた要件を次の基準で分ける。

- **横断要件（`docs/nfr.md`）**: 各機能が作るときに守る基準。例: 「一覧画面は 1,000 件で 2 秒以内に表示する」「個人情報をログに出さない」
- **運用基盤（`999-app-nfr.md`）**: 1 回作れば全体に効く仕組み。例: 「稼働を外部から監視し、停止したら通知する」「毎日バックアップを取り、月 1 回リストアを確認する」「main へのマージでテストとデプロイを自動で行う」

### ステップ 4: 書き出し案の提示と合意

次をまとめて提示し、承認を得る。

1. `docs/nfr.md` の要件の一覧（ID、区分、MVP 時の値、成長時の値、確認方法）
2. `999-app-nfr.md` の主な要求
3. 999 を `spec_order.md` のどこに置くか。既定は **MVP の最後の機能の後、拡張の機能の前**。本番公開の前に運用基盤が要るためである。先に入れたい場合は位置を相談する（依存の順序は守る）。
4. 目標のうち、今の構成では達成できないもの（あれば）と、その対応

### ステップ 5: 書き出し

- `docs/nfr.md` を [templates/nfr.md](./templates/nfr.md) に沿って書く。
- `999-app-nfr.md` を書く。ヘッダは `**状態**: 未着手 | **区分**: MVP | **想定順序**: 999 | **依存**: 000-app-basic`（000 がなければ `—`）とする。「前提・設計原則との関係」に `docs/nfr.md` の対応する ID を書く。
- `README.md` の一覧と `spec_order.md` に 999 の行を足す。
- 憲章に `docs/nfr.md` を参照する条項がなければ、`speckit-constitution` の手順で足す（例: 「すべての機能は docs/nfr.md の横断要件を満たす。plan.md の憲章チェックで確認する」）。

### ステップ 6: 検証

```bash
python3 <skills>/speckit-concept-2-feature/scripts/validate.py docs/feature
```

`<skills>` は、このスキルが置かれた skills ディレクトリである。`python3` がない環境では `python` または `py -3` に読み替える。エラーが 0 件になるまで直す。

### ステップ 7: 報告

- `docs/nfr.md` の要件の件数（区分ごと）と、主な目標値
- `999-app-nfr.md` の主な要求と、`spec_order.md` での位置
- 今の構成では達成できない目標（あれば）と、その対応
- 次の手順の案内（`speckit-all` で 000 から順に仕様化・実装する。`speckit-bootstrap` の中で実行している場合は、その手順に戻る）

## 3. 記述の規則

- `docs/nfr.md` の各要件には、ID、MVP 時の値、成長時の値、確認方法（テスト、監視、レビューなど）を書く。
- 999 には、仕組みの「何ができればよいか」を書き、使うサービスやツールは `docs/architecture.md` に従う。
- 各機能の性能要件のうち、その機能だけに効くもの（特定の画面の応答時間など）は、その機能の `spec.md` で決める。`docs/nfr.md` には全体の既定値を書く。

## 4. 更新モード

- `docs/nfr.md` を変えるときは、差分と影響（すでに `spec化済み` 以降の機能が新しい基準を満たすか）を示し、合意した変更だけを反映する。「変更履歴」に日付、内容、理由を足す。
- `999-app-nfr.md` が `spec化済み` 以降なら書き換えない。追加が必要なものは、通常の番号の新しい機能として提案する。

## 5. 禁止事項

- 構成と費用で達成できない目標を、注記なしに書くこと
- 測れない形（「高速に」「十分に」など）で要件を書くこと
- ユーザーの合意なしに書き出す、または上書きすること
- 状態が `spec化済み` 以降の機能ファイルを書き換えること
